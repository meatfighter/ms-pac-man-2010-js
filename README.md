# Ms. Pac-Man 2010 JS

This repository contains the browser and desktop release project for Ms. Pac-Man 2010. The browser version is a TypeScript PWA port of the original Java game, using the public `slick2d-ts` package for the Slick2D-style runtime layer. The desktop version keeps the Java game buildable and distributable as a legacy runnable artifact.

The production web release is more than a Vite build. It includes the about page, the PWA, the Java desktop download, source archives, release metadata, checksums, high-score client configuration, and safety checks that make the generated `dist/` tree relocatable and reproducible enough to deploy unchanged from staging to production.

## Repository Layout

- `about/` contains the static project/about page. The production release puts this at the top of `dist/`, with a play link into the PWA.
- `assets/` contains source assets shared by generated pages and icons.
- `desktop/` contains the Java desktop version, Maven project files, runtime dependency notes, license material, native libraries, and Java sources.
- `pwa/` contains the TypeScript browser PWA. `pwa/src/app/` is the browser shell, menu, loading, storage, and app bootstrap. `pwa/src/mspacman/` is the game port. `pwa/public/` contains the manifest, service worker, and static PWA assets.
- `scripts/` contains build, verification, HMAC, release, preview, and test tooling.
- `dist/` is generated by the canonical production build. Upload this tree, not individual source folders.
- `releases/` is a local staging folder for desktop release ZIPs.
- `.release-secrets/` is local-only and ignored by Git. It stores the active high-score submission HMAC key and temporary finalization journal files.
- `.release-candidates/` is local-only and ignored by Git. It stores verified next-key release candidates during HMAC rotation.
- `.release-components/` is local-only and ignored by Git. It stores noncanonical component builds and synthetic release-test artifacts.

Generated local state such as `node_modules/`, `dist/`, `.release-components/`, `.release-candidates/`, `.release-secrets/`, `desktop/target/`, `.dist-pending-*`, `.dist-previous-*`, and `.dist-active-before-hmac-finalize-*` should not be included in review/source-export archives.

## Project Pieces

The PWA is the browser game. It is a single-page app with a menu-first shell because browser audio requires a user gesture before Web Audio can reliably play. The menu also owns volume, New Game/Continue, and the transition into the game canvas. The game itself can return to the menu through the in-game hamburger button.

The about page is static and separate from the PWA. It is built into the same release tree and links to the generated PWA location using deployment-relative paths.

The desktop build is the preserved Java version. The scripts build a runnable JAR and ZIP using the local Java/Maven toolchain and package the required runtime files, native libraries, license texts, and LGPL corresponding-source material.

The high-score server is not in this repository. The clients talk to `/api/ms-pac-man-2010/scores` in production. Browser builds deliberately use same-origin API paths because the server is not intended to provide CORS.

## Development Commands

```text
npm.cmd ci --ignore-scripts
npm.cmd run dev
```

`npm.cmd run dev` starts the PWA dev server. For local unsigned development, score downloads can run, but submissions remain local-only unless a valid key is supplied through the supported release/test paths.

Common checks:

```text
npm.cmd test
npm.cmd run lint
npm.cmd run format:check
npm.cmd audit --audit-level=high
```

Useful targeted commands:

- `npm.cmd run verify:pwa-build` verifies an existing generated PWA build.
- `npm.cmd run build:pwa:unsigned` builds a local unsigned PWA component with score submission disabled.
- `npm.cmd run build:web:unsigned` builds local unsigned web component artifacts.
- `npm.cmd run build:desktop` builds an unsigned desktop Java JAR and ZIP.
- `npm.cmd run build:desktop:release` builds the desktop Java JAR and ZIP with the selected release HMAC key embedded.
- `npm.cmd run release:desktop` refreshes the staged desktop release ZIP in `releases/`.
- `npm.cmd run run:desktop` launches the built desktop JAR with the local native libraries.
- `npm.cmd run preview:release -- --base=/test-location/` serves the already-built `dist/` tree under a synthetic mount path without rebuilding or rewriting it.

## Script Organization

The scripts are grouped by responsibility rather than by one giant release script.

- `build-release.mjs`, `release-output-plan.mjs`, `build-utils.mjs`, and the `build-*` wrappers decide what kind of artifact is being built, which HMAC key source is allowed, where output may go, and how the child build steps receive their environment.
- `assemble.mjs`, `build-about.mjs`, `build-desktop.mjs`, `generate-icons.mjs`, `write-release-metadata.mjs`, `write-release-checksums.mjs`, and `write-source-archive.mjs` create the concrete release files.
- `verify-pwa-build.mjs` and `verify-release.mjs` prove that generated output has the expected PWA precache list, metadata, source archives, desktop ZIP contents, deployment paths, HMAC fingerprint, and checksums.
- `release-io.mjs`, `release-lock.mjs`, and `release-dist-promotion.mjs` provide shared filesystem safety: strict walkers, symlink/junction rejection, atomic writes/copies, release locks, and journaled `dist/` promotion.
- `hmac-config.mjs`, `hmac-cli.mjs`, `release-provision.mjs`, `release-rotate-hmac.mjs`, `release-finalize-hmac.mjs`, and `smoke-production-api.mjs` manage local key files, HMAC rotation, finalization, and production API smoke testing.
- `preview-release.mjs` serves an already-built release tree under a synthetic base path so relocatability can be tested without rebuilding.
- `test-*.mjs` files are plain Node-based regression tests for the PWA, high-score protocol, desktop protocol, release hardening, HMAC flows, and failure recovery.

## Build Types

There are three important output categories.

Component builds are useful for local inspection or qualification. They write under `.release-components/` and are not the canonical production site bundle. Examples include `build:pwa:release`, `build:web`, `build:pwa:unsigned`, and `build:web:unsigned`.

The canonical production build is:

```text
npm.cmd run build
```

It builds the PWA, about page, desktop download, source archives, metadata, and checksums into a temporary pending tree, verifies that tree, then atomically promotes it to `dist/`.

Synthetic full releases are test-only full release builds with a known fake HMAC key. They are useful for automated review without printing or using the real production key:

```text
set MSPACMAN_HMAC_KEY_HEX=000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
node scripts/build-release.mjs --target=full --key-source=env
```

Synthetic releases write to `.release-components/synthetic-full/`.

## Versioning And Cache Identity

The app version lives in `version.json`, `package.json`, and `desktop/pom.xml`; release builds verify that these versions match.

Release builds use a fresh in-memory build stamp passed through the build environment. The scripts do not rewrite tracked `version.json` just to stamp a release. This avoids leaving the source tree dirty if a process is killed mid-build.

The PWA service-worker cache identity includes the application version, the build stamp, and either an unsigned marker or the selected HMAC key fingerprint. Resource URLs also include release cache keys where appropriate. This prevents stable-path resources from silently aliasing an older release in the browser cache.

The PWA release verifier enumerates the generated PWA tree and verifies that everything intended for precaching is represented exactly once in the service-worker static resource list.

## Relocatable Web Releases

The generated `dist/` tree is intended to be copied unchanged beneath any directory on `https://meatfighter.com/`, such as `/ms-pac-man-2010-staging/` or `/ms-pac-man-2010/`.

Static links in the generated about page and PWA are deployment-relative. Do not hard-code `/pwa/`, `/mspacman2010/`, `/ms-pac-man-2010/`, or staging paths into runtime assets.

The high-score API is the intentional exception: the PWA uses the root-relative `/api/ms-pac-man-2010/scores` path so any same-origin deployment directory talks to the same production API.

The service worker is registered relative to the current PWA page, and its Cache Storage namespace includes the service-worker scope path. This lets staging and production copies coexist on the same origin without deleting each other's caches.

Browser save-state and volume local-storage keys include the encoded deployment path. Staging and production copies on the same origin therefore keep separate saved games and volume settings without migrating legacy keys.

`npm.cmd run verify:release` and the release pipeline check generated files for accidental hard-coded deployment roots and exercise multiple synthetic PWA mount paths.

## High-Score HMAC Model

Release clients sign high-score submissions with an HMAC key. This is a release coordination and spam-resistance control, not a true client secret. Production PWA JavaScript and release desktop JARs are inspectable by users, so the high-score server must independently validate every submitted score.

Unsigned/dev PWA builds use `MSPACMAN_SCORE_API_URL` when set, otherwise `/api/ms-pac-man-2010/scores`; release PWA builds require the fixed `/api/ms-pac-man-2010/scores` endpoint.

Desktop Java uses `MSPACMAN_SCORE_API_URL` or `-Dmspacman.scoreApiUrl=...`; otherwise it defaults to `https://meatfighter.com/api/ms-pac-man-2010/scores`.

Desktop Java release builds embed the selected release key in generated `desktop/target/classes/mspacman/high-score-release.properties` before packaging the JAR. Runtime Java key precedence is:

1. `-Dmspacman.hmacKeyHex`
2. `MSPACMAN_HMAC_KEY_HEX`
3. embedded release resource
4. no key

Explicit malformed JVM property or environment values disable remote submission and do not fall back. Without a valid key, downloads still run and submissions remain local-only.

`.release-secrets/` must never be copied into `dist/`, `releases/`, desktop ZIPs, or generated source archives. `hmac:check` scans tracked files for active and staged next keys and prints fingerprints only. `hmac:show` prints the real key and should be used only when deliberately provisioning the server.

## HMAC Commands

One-time setup with an existing production server key:

```text
npm.cmd run hmac:import
npm.cmd run hmac:check
```

`hmac:import` uses a hidden prompt and refuses to overwrite an existing active key. The imported value must match the key configured in `/etc/ms-pac-man-2010-server.env`.

Other HMAC commands:

- `npm.cmd run hmac:init` creates a local active release key if one does not already exist.
- `npm.cmd run hmac:check` validates local key files, reports staged rotation state, verifies ignored/untracked secret storage, scans tracked files for leaks, and prints fingerprints only.
- `npm.cmd run hmac:show` prints the active key. Use this only when provisioning the server.
- `npm.cmd run hmac:rotate:prepare` stages a next key.
- `npm.cmd run hmac:rotate:check` validates active and next keys.
- `npm.cmd run hmac:rotate:show-next` prints the staged next key. Use this only when deliberately updating the server.
- `npm.cmd run hmac:rotate:abort` removes a staged next key and local candidate before server cutover.

An ordinary active-key release refuses to run while `.release-secrets/ms-pac-man-2010-hmac.next.hex` exists. Finish and finalize the rotation, or abort it before shipping another active-key release.

## Release Safety Model

The release tooling has several guardrails because it writes generated artifacts, promotes directories, and handles local HMAC material.

Public active/next-key release commands require a clean Git tree before building. Component and synthetic test builds can run in development contexts, but production release commands reject dirty source.

Release and unsigned component builds pass a transient build stamp through the build environment and do not rewrite tracked `version.json`.

Release output paths are allowlisted. User-facing production release commands do not accept arbitrary output directories. Test-only path overrides require explicit test gates.

Generated-output mutations reject symlink and junction traversal. The path checks validate the managed root, each existing intermediate path component, and generated file destinations themselves. A destination such as `releases/example.zip` must be a regular file or absent; a symlink/junction at that exact file path is rejected.

Release file walkers reject linked roots and linked children. This matters for verification, source archives, PWA precache checks, preview servers, and any code that recursively inspects generated output.

Atomic writes and copies use temporary files, fsync where supported, and rename. Temporary files are cleaned on pre-rename failures. Desktop release ZIP staging also uses atomic copy rather than direct overwrite.

Full release promotion uses a pending directory and a journaled promotion flow. Failures before the final pending-to-`dist/` rename recover to the old release; failures after the commit point recover to the new release and clean up transaction state.

Release operations use a lock in `.release-secrets/`. Nested child operations register as lock holders so stale-lock recovery cannot remove a lock while a child build is still mutating artifacts. Lock holder updates are serialized with a short-lived update guard, and update-guard recovery treats `ENOENT` as a normal race where another process already released or recovered the guard.

## Generated Release Artifacts

A canonical `dist/` release includes:

- `dist/index.html` and about-page assets.
- `dist/pwa/` with the PWA, service worker, manifest, icons, and static game assets.
- `dist/pwa/THIRD_PARTY_NOTICES.txt`, generated from the root `THIRD_PARTY_NOTICES.md`.
- `dist/downloads/ms-pac-man-2010-js-source.zip` and a matching versioned source ZIP, generated with `git archive` from the exact `release.json` commit. These contain committed source only, never arbitrary untracked checkout files.
- `dist/downloads/ms-pac-man-2010-desktop.zip` and a matching versioned desktop ZIP, copied from the exact release desktop artifact.
- `dist/release.json`, containing app version, build stamp, pre-build Git commit, pre-build Git tree state, release kind, HMAC key source, PWA cache identity, deployment metadata, source archive metadata, and HMAC fingerprint. It never contains the full HMAC key.
- `dist/checksums.sha256`, covering every generated release file except itself.

`smoke:production-api` verifies the selected release artifact before contacting production. It uses the fixed `https://meatfighter.com/api/ms-pac-man-2010/scores` endpoint, performs a duplicate score POST that must not mutate the table, and refuses to POST if the production table is empty.

## Testing

`npm.cmd test` runs the main automated suite:

- PWA save/restore and corrupted local-storage recovery.
- PWA high-score protocol and HMAC behavior.
- PWA build configuration and unsigned build behavior.
- PWA release script cache-stamp behavior.
- Release output path planning and provenance validation.
- Release IO symlink/junction and atomic-write/copy hardening.
- Release lock concurrency, stale recovery, malformed-lock recovery, and nested holder tracking.
- Atomic `dist/` promotion recovery.
- HMAC config, import, rotation, and leak scanning.
- Preview-server relocation and symlink rejection.
- Release safety and failure recovery.
- HMAC finalization and exact-candidate promotion.
- Production API smoke-test logic against a mock server.
- Desktop Java high-score protocol tests.

Run `npm.cmd run lint`, `npm.cmd run format:check`, and `npm.cmd audit --audit-level=high` as separate release qualification gates. `npm audit` is intentionally not part of the deterministic build command because it depends on the external advisory service.

## Production Release Workflow

From an already configured release workstation:

```text
git status --porcelain
npm.cmd ci --ignore-scripts
npm.cmd run hmac:check
npm.cmd test
npm.cmd run lint
npm.cmd run format:check
npm.cmd audit --audit-level=high
npm.cmd run build
npm.cmd run verify:release
npm.cmd run smoke:production-api -- --confirm-production
git status --porcelain
```

Both `git status --porcelain` commands should produce no output. After `npm.cmd run build`, inspect `dist/release.json` and confirm:

```text
releaseKind   = production
hmacKeySource = active
gitTreeState  = clean
gitCommit     = current HEAD
```

Compare the `hmacKeyFingerprint` in `dist/release.json` with the active fingerprint printed by `npm.cmd run hmac:check`.

Then stage and promote the exact generated `dist/` bytes:

1. Upload that exact `dist/` content beneath `/ms-pac-man-2010-staging/`.
2. Test the staged client against the production same-origin API at `/api/ms-pac-man-2010/` while leaving the historical `/mspacman2010/` site untouched.
3. Exercise the PWA online/offline, score GET, non-mutating authenticated POST, desktop ZIP, keyboard, gamepad, audio, and fullscreen behavior.
4. Promote the same release bytes beneath `/ms-pac-man-2010/`; do not rebuild or rewrite files for the final location.
5. Verify deployed checksums against `dist/checksums.sha256`.
6. Update public links to point at `/ms-pac-man-2010/`.
7. Only after production acceptance, configure the old `/mspacman2010/` location to redirect to `/ms-pac-man-2010/`.
8. Separately archive or disable the old writable score CGI only after migration and historical-score review are complete.

## New Deployment Provisioning

For a brand-new production server key:

```text
npm.cmd run release:provision
npm.cmd run hmac:show
```

`release:provision` creates a new active local key and performs a complete verified full release. It does not modify the server. Use `hmac:show` only when deliberately provisioning the server. Manually install the shown value as `MSPACMAN_HMAC_KEY_HEX` in the server environment, restart the server, and verify the deployment.

## HMAC Rotation Workflow

Rotation uses a staged next key and a verified candidate release. The central rule is that finalization promotes the exact candidate bytes that were already tested with the new key.

```text
npm.cmd run release:rotate-hmac
npm.cmd run hmac:rotate:show-next

# Manually install key B on the production server and restart the service.

npm.cmd run smoke:production-api -- --confirm-production --key-source=next

# Only after the production B-key smoke test succeeds:
npm.cmd run release:finalize-hmac
```

Preferred cutover order:

1. Build and verify the next-key candidate with `npm.cmd run release:rotate-hmac`.
2. Stage the exact candidate bytes from `.release-candidates/hmac-next/`.
3. Test everything possible before key cutover.
4. Manually replace `MSPACMAN_HMAC_KEY_HEX` on the server from active A to next B, then restart `ms-pac-man-2010.service`.
5. Immediately perform the final valid B-key public API test with `npm.cmd run smoke:production-api -- --confirm-production --key-source=next`.
6. Run `npm.cmd run release:finalize-hmac` locally.
7. Promote the exact finalized bytes to the final static location.

`release:finalize-hmac` verifies the already-tested `.release-candidates/hmac-next/` bytes, promotes those exact bytes to `dist/`, and promotes the staged next HMAC key to active. It does not rebuild the client. If interrupted mid-finalization, rerun `npm.cmd run release:finalize-hmac`; it uses a non-secret journal in `.release-secrets/` to complete or clean up the interrupted promotion.

After finalization, `dist/release.json` intentionally retains `rotation-candidate/next` build provenance because finalization promotes the exact previously tested candidate bytes without rewriting them. Ordinary active-key production smoke testing accepts this finalized candidate only when the artifact fingerprint matches the active key.

Never run `release:finalize-hmac` after server key B has been generated but before the production B-key API smoke test has succeeded.

Before server cutover, `npm.cmd run hmac:rotate:abort` is allowed if the staged next key and candidate should be discarded.

After server cutover from active A to next B, do not delete `.release-secrets/ms-pac-man-2010-hmac.next.hex` and do not delete `.release-candidates/hmac-next/`. If the rotation must be rolled back after server cutover:

1. Restore `MSPACMAN_HMAC_KEY_HEX=A` on the production server.
2. Restart `ms-pac-man-2010.service`.
3. Verify public GET.
4. Verify an A-key client or controlled POST path works as appropriate.
5. Verify the server fingerprint matches local active A.
6. Only then run `npm.cmd run hmac:rotate:abort` locally.

If the B key/server is healthy and only staging or static deployment needs repair, keep the server on B, preserve `.next` and the candidate, repair/retest, then continue to `release:finalize-hmac`.

Do not automate SSH or root-owned server configuration changes from this repository.

## Fingerprint Comparison

To compare the local active-key fingerprint with the production server without printing the key:

```text
npm.cmd run hmac:check
```

On the server, an administrator can print the same 12-character fingerprint from `/etc/ms-pac-man-2010-server.env` without displaying the key:

```sh
sudo bash -lc 'set -a; source /etc/ms-pac-man-2010-server.env; set +a; printf "%s" "$MSPACMAN_HMAC_KEY_HEX" | xxd -r -p | sha256sum | cut -c1-12'
```
